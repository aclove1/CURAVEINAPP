### C-3. Credentialing ramp converges on 85 % commercial, but `effectiveCommercialShare` returns 75 % — steady-state blended rate disagrees with monthly blended rate

**Issue.** `lib/model.ts:46`:

```ts
const CRED_RAMP_COMM = [0.40, 0.53, 0.67, 0.80, 0.85, 0.85, ..., 0.85]
```

This ramp is hardcoded to 0.85 commercial for M5–M12, i.e. it assumes the Forney payer mix (15/85). Meanwhile:

- Default `market` = `newBraunfels` → `commercialMix = 0.75`, `medicareMix = 0.25`.
- With V12 hardening ON, `effectiveCommercialShare(a) = 0.75` (TARGETED_COMMERCIAL_SHARE.base).
- `calcOverallBlendedRate` uses `effectiveCommercialShare(a) = 0.75`.
- `calcMonthBlendedRate(month>=5)` uses `commMix = 0.85`.

So the monthly blended rate (M5–M12) is computed against a 0.85 commercial share, while `calcOverallBlendedRate` (used in breakeven) uses 0.75. The two numbers diverge by ~$64/proc.

**Impact.** Breakeven procs per month is understated. Monthly revenue reflects 85% commercial despite the operator selecting New Braunfels (75/25) or a Down-case targeted share (65/35).

**Fix.** Derive the ramp endpoint from `effectiveCommercialShare(a)` rather than hardcoding 0.85. Replace the constant array with a function:

```ts
// lib/model.ts — replace CRED_RAMP_COMM and getCredentialingMix
function getCredentialingMix(month: number, a: Assumptions): { govMix: number; commMix: number } {
  const steady = effectiveCommercialShare(a)                // 0.65 / 0.75 / 0.85
  // Linear ramp M1 @ 0.40 → M5 @ steady, then hold.
  const RAMP_START = 0.40
  const RAMP_MONTHS = 5
  const commMix = month <= 1
    ? RAMP_START
    : month >= RAMP_MONTHS
      ? steady
      : RAMP_START + ((steady - RAMP_START) * (month - 1) / (RAMP_MONTHS - 1))
  return { govMix: 1 - commMix, commMix }
}
```

This makes monthly revenue, overall blended rate, and breakeven internally consistent at any scenario.

### C-4. `y2VolumeGrowth` / `y3VolumeGrowth` sliders on `/scenario` page do nothing

**Issue.** Verified via `grep`: `y2VolumeGrowth` and `y3VolumeGrowth` are declared in `Assumptions` (types.ts:135-136), seeded in `DEFAULT_ASSUMPTIONS` (defaults.ts:246-247), exposed as editable sliders in `app/scenario/page.tsx:486-487`, emitted in `app/api/audit/route.ts:74-75`, and **referenced nowhere in `lib/model.ts`**. **Impact.** Operator drags the "Y2 Volume Growth" slider from 39% to 80% → nothing changes in the dashboard, P&L, revenue, or any downstream page. A diligence reviewer who notices this loses trust in the whole tool.

Option 1 is faster and aligns with the current "conversion-rate-driven YoY improvement" model. Option 2 gives the operator an explicit growth knob and is more defensible for investors. **Recommend Option 2**; investors expect to see and tune a growth rate.

### S-4. Personnel cost is flat all 12 months — ignores hiring ramp

**Issue.** `calcPersonnelCost(a)` = (physician + RVT + MA + front office) × 1.40 / 12, applied uniformly M1–M12. In reality Y1 M1 does not run a full staff at $421k annualized salaries. An operator launching with 60 procs/mo (well below the ~146 ceiling) likely starts with 0.5 FTE physician + 0.5 FTE MA, scaling up.

**Impact.** Overstates OpEx in M1–M6 by likely $20–30k/mo, understates Y1 EBITDA / overstates cash burn. For a pre-revenue investor pitch this matters: stating a $800k+ OpEx nut the day you open is not how a ramped practice actually looks.

**Fix.** Add a headcount ramp to each role:

```ts
// lib/types.ts — extend role entries
interface RoleRamp { startMonth: number; endMonth: number; startFte: number; endFte: number }
// default: physician { startMonth: 1, endMonth: 12, startFte: 0.5, endFte: 1.0 }
// RVT/MA/front: { startMonth: 1, endMonth: 6, startFte: 0.5, endFte: 1.0 }

function fteAtMonth(r: RoleRamp, month: number): number {
  if (month <= r.startMonth) return r.startFte
  if (month >= r.endMonth)   return r.endFte
  return r.startFte + (r.endFte - r.startFte) * (month - r.startMonth) / (r.endMonth - r.startMonth)
}
// calcOpexMonth uses Σ (fteAtMonth × annualSalary × (1+tax+benefits) / 12) per role.
```

Flag: if operator confirms they are hiring full staff day 1 (physician employment contract already signed), leave flat but add an explicit tooltip: "assumes full staff from M1". Don't leave this silent.

### S-5. Rounding intermediate funnel stages amplifies variance at low volume

**Issue.** `calcFunnelMonth`:
```
leads    = round(spend / cpl)
contacts = round(leads × contactRate)
booked   = round(contacts × bookingRate)
shows    = round(booked × showRate)
treated  = round(shows × treatmentConversion)
rawProcs = round(treated × procsPerPatient)
```

Six successive `round` calls compound. At M1 Base spend $3,500 / CPL $60 = 58.33 → 58 leads. ×0.53 → 30.74 → 31 contacts. ×0.60 → 18.6 → 19 booked. ×0.78 → 14.82 → 15 shows. ×0.65 → 9.75 → 10 treated. ×3.4 → 34 procs. The true unrounded composite is 3,500 × 0.53/60 × 0.60 × 0.78 × 0.65 × 3.4 = 53.4 procs; the rounded path gives 34. That's a **36 % undercount** at M1, decaying as volume grows.

**Impact.** M1-M3 dashboards consistently underreport ramp economics. Annual totals are less affected but still 2–5 % low.

**Fix.** Keep the stage math continuous and round only when displaying:

```ts
// lib/model.ts — calcFunnelMonth
const spend = svArr(a.marketingSpend, a.scenario)[idx] ?? 0
const cpl = sv(a.cpl, a.scenario)
const leadsF     = safeDivide(spend, cpl)
const contactsF  = leadsF     * sv(a.contactRate, a.scenario)
const bookedF    = contactsF  * sv(a.bookingRate, a.scenario)
const showsF     = bookedF    * sv(a.showRate, a.scenario)
const treatedF   = showsF     * sv(a.treatmentConversion, a.scenario)
const rawProcsF  = treatedF   * effectiveProcsPerPatient(a)

const cappedProcsF = Math.min(rawProcsF, a.maxCapacityPerMonth)
const utilization  = a.maxCapacityPerMonth > 0 ? cappedProcsF / a.maxCapacityPerMonth : 0
const excessDemand = Math.max(0, rawProcsF - a.maxCapacityPerMonth)

return {
  month,
  leads:      Math.round(leadsF),
  contacts:   Math.round(contactsF),
  booked:     Math.round(bookedF),
  shows:      Math.round(showsF),
  treated:    Math.round(treatedF),
  rawProcs:   Math.round(rawProcsF),
  cappedProcs: Math.round(cappedProcsF),
  utilization,
  excessDemand: Math.round(excessDemand),
  marketingSpend: spend,
}
```

Revenue / COGS downstream already multiplies against `cappedProcs` — keeping them rounded avoids breaking the FunnelBridge reconciliation checks (`plProcsMatch`).

// lib/model.ts
const WEIGHTED_MEDICARE_BASE = FEE_SCHEDULE.reduce((s, f) => s + f.medicareFee * f.volumeShare, 0)
